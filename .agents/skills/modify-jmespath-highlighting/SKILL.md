# Modify JMESPath Highlighting

## Rules (read first)

1. **DO NOT scan the project.** Do NOT run `glob`, `grep`, or broad file searches to rediscover the layout. Every file you need is listed below with its exact path and role. Only read/edit the targeted files listed here. This is a token-efficiency requirement.
2. **DO NOT hand-edit generated code.** Anything under `build/generated-src/antlr/` is regenerated by Gradle.
3. All paths below are relative to the project root (the directory containing `build.gradle.kts`).

## How highlighting works (two mechanisms)

A color can attach to a rule in **one of two ways**, depending on whether that rule becomes a *lexer token* or a *PSI node*:

- **Token-level (lexer rule).** Lexer rules in `JmesPath.g4` (`NAME`, `STRING`, `JSON_CONSTANT`, `COMPARATOR`, literals like `'@'`, `'{'`, …) map to an IntelliJ token in `JMESPathTokenTypes.getIElementType`. Those tokens are colored directly in `JMESPathSyntaxHighlighter.getTokenHighlights`. This is the path for anything that is purely lexical (keywords, strings, numbers, operators, brackets, `@`, …).
- **PSI-level (parser rule).** Parser rules that produce a *composite/leaf PSI node* (e.g. `keyName` → `KEY_NAME`) do **not** have their own lexer token — the lexer only sees the underlying token (e.g. `NAME`), which can appear in many contexts. To give such a rule its own color you must add an **Annotator** that highlights the PSI element, plus register it in `plugin.xml`. This is the path used for `keyName`.

Rule of thumb: if the rule is **UPPERCASE** in the grammar (a lexer rule) or a bare literal, use the token path. If it is **lowercase** (a parser rule), use the annotator path.

## Targeted file map

### 1. Syntax source of truth (read to identify the rule)
- `src/main/antlr/JmesPath.g4`
  - Parser rules lowercase (`expression`, `keyName`, `keyvalExpr`), lexer rules UPPERCASE (`NAME`, `STRING`, `JSON_CONSTANT`). Literal tokens (`'.'`, `'{'`, `'[?'`, `'('`, `'@'`, …) become implicit `T__n` lexer constants.

### 2. Token-level highlighting (edit for lexer-rule colors)
- `src/main/kotlin/my/example/jmespath/JMESPathTokenTypes.kt`
  - `@JvmField` token-type constants (`IDENTIFIER`, `STRING`, `KEYWORD`, `CURRENT_NODE`, `FUNCTION`, `NUMBER`, `COMPARATOR`, `OPERATOR`, `LPAREN`/`RPAREN`, `LBRACKET`/`RBRACKET`, `LBRACE`/`RBRACE`, `COMMA`, `COLON`, `LITERAL_TICK`, `BAD_CHARACTER`, `WHITE_SPACE`).
  - `getIElementType(antlrTokenType)`: `when` over `JmesPathLexer.*` maps each ANTLR token → IntelliJ token.
  - ⚠️ **Fragile:** literal tokens are referenced by generated index (`T__0`..`T__17`). Adding a new literal to the grammar renumbers these and silently breaks the mapping. Re-verify every `T__n` against regenerated `JmesPathLexer.java` if you touch literals.
- `src/main/kotlin/my/example/jmespath/JMESPathSyntaxHighlighter.kt`
  - `companion object` defines a `TextAttributesKey` per color (e.g. `KEYWORD`, `FUNCTION`, `KEY_NAME`, `STRING`, …), each with a `DefaultLanguageHighlighterColors.*` fallback.
  - `getTokenHighlights(tokenType)`: `when` mapping token → `arrayOf(key)`. Return `EMPTY_KEYS` to give a token **no** dedicated color.

### 3. Lexer adapter (edit only if the token needs re-tagging based on context)
- `src/main/kotlin/my/example/jmespath/JMESPathLexer.kt`
  - Wraps the generated ANTLR lexer. Special-case near line 90 re-tags a `NAME` as `FUNCTION` when followed by `(` or matching `BUILTIN_FUNCTIONS`.

### 4. PSI-level highlighting (edit for parser-rule colors, e.g. `keyName`)
- `src/main/kotlin/my/example/jmespath/JMESPathElementTypes.kt` — PSI element constants (`KEY_NAME`, `KEYVAL_EXPR`, `OBJECT_HASH`, …). The node must already exist here (produced by the parser).
- `src/main/kotlin/my/example/jmespath/JMESPathPsiParser.kt` — the hand-written parser that produces the PSI node (e.g. `KEY_NAME` at ~lines 154–156). Only read to confirm which node a rule becomes.
- `src/main/kotlin/my/example/jmespath/JMESPathSyntaxAnnotator.kt` — the annotator. Pattern:
  ```kotlin
  if (element.node.elementType == JMESPathElementTypes.KEY_NAME) {
      holder.newSilentAnnotation(HighlightSeverity.INFORMATION)
          .range(element.textRange)
          .textAttributes(JMESPathSyntaxHighlighter.KEY_NAME)
          .create()
  }
  ```
- `src/main/resources/META-INF/plugin.xml` — register a new annotator:
  ```xml
  <annotator language="JMESPath" implementationClass="my.example.jmespath.JMESPathSyntaxAnnotator"/>
  ```

### 5. Color settings page + labels (edit whenever a color key is added/removed/renamed)
- `src/main/kotlin/my/example/jmespath/JMESPathColorSettingsPage.kt` — `AttributesDescriptor(messageKey, TextAttributesKey)` per color; also `getDemoText()`.
- `src/main/resources/messages/MyMessageBundle.properties` — label keys (`jmespath.colors.keyword`, `jmespath.colors.key_name`, …). Add/remove a `jmespath.colors.*` entry to match each descriptor.

### 6. Tests
- `src/test/kotlin/my/example/jmespath/JMESPathHighlightingTest.kt`
  - `testSyntaxHighlighterAttributes` asserts each token → expected `TextAttributesKey` (and empty for non-colored tokens like `IDENTIFIER`).
  - `testColorSettingsPage` asserts each color key is present as an `AttributesDescriptor`.
  - `testSyntaxAnnotatorRegisteredInLanguage` verifies annotator registration via `ExtensionPointName.create<LanguageExtensionPoint<Annotator>>("com.intellij.annotator").extensionList` — check `it.language == JMESPathLanguage.INSTANCE.id && it.instance is …`. (Do **not** use `Annotator.forLanguage` / `LanguageAnnotators`: they are not on this platform-only classpath.)

## Workflow

1. Read `src/main/antlr/JmesPath.g4` and identify the target rule.
2. Decide token-level vs PSI-level (see above).
3. Make the change in `JMESPathSyntaxHighlighter.kt` (and `JMESPathTokenTypes.kt` if the mapping must change). For PSI-level colors add/update `JMESPathSyntaxAnnotator.kt` and register in `plugin.xml`.
4. Update `JMESPathColorSettingsPage.kt` and `MyMessageBundle.properties`.
5. Update tests in `JMESPathHighlightingTest.kt`.
6. Run (export JDK first):
   ```bash
   ./gradlew test
   ```

## Gotchas

- **Token vs PSI mismatch is the top failure mode.** `NAME` is a *token* (colored in the highlighter); `keyName` is a *PSI node* (colored only via an annotator). Do not try to color a parser rule from `getTokenHighlights`.
- Removing a token's color: map it to `EMPTY_KEYS`, do not leave a dangling key.
- `DefaultLanguageHighlighterColors.INSTANCE_FIELD` is the conventional fallback for key/property-name colors.
- Annotator registration is language-scoped (`<annotator language="JMESPath" …>`); the `com.intellij.annotator` extension point stores `LanguageExtensionPoint` beans, not raw `Annotator` instances.
