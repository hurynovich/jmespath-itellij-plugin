# Modify JMESPath Syntax

## Rules (read first)

1. **DO NOT scan the project.** Do NOT run `glob`, `grep`, or broad file searches to rediscover the layout. Every file you need is listed below with its exact path and role. Only read/edit the targeted files listed in the relevant section. This is a token-efficiency requirement.
2. **DO NOT hand-edit generated code.** Anything under `build/generated-src/antlr/` is regenerated by Gradle.
3. All paths below are relative to the project root (the directory containing `build.gradle.kts`).

## Architecture in one paragraph

`src/main/antlr/JmesPath.g4` is the single source of truth for syntax. ANTLR generates a lexer + parser into `build/generated-src/antlr/main/my/example/jmespath/`. At runtime the plugin uses the **generated lexer** (wrapped by `JMESPathLexer`) but a **hand-written recursive-descent parser** (`JMESPathPsiParser`) that must be kept manually in sync with the grammar. Token types and PSI element types are separate Kotlin objects that mirror the grammar.

## Targeted file map

### 1. Syntax source of truth (edit first)
- `src/main/antlr/JmesPath.g4`
  - Parser rules are lowercase (`expression`, `keyvalExpr`), lexer rules UPPERCASE (`NAME`, `STRING`). Adding a parser rule gives you a dedicated context node + visitor method; adding a lexer rule gives you a new token type.
  - Literal tokens (`'.'`, `'{'`, `'[?'`, `'('`, etc.) become implicit `T__n` lexer constants.

### 2. Token types + ANTLR→IntelliJ mapping (edit when adding a lexer token)
- `src/main/kotlin/my/example/jmespath/JMESPathTokenTypes.kt`
  - `JMESPathTokenTypes` object: `@JvmField` token-type constants (`IDENTIFIER`, `STRING`, `KEYWORD`, ...) and `BUILTIN_FUNCTIONS` set.
  - `getIElementType(antlrTokenType: Int)`: `when` over `JmesPathLexer.*` constants mapping each ANTLR token to an IntelliJ token.
  - ⚠️ **Fragile:** it references literal tokens by generated index (`T__0`..`T__17`). Adding any **new literal** to the grammar renumbers these and silently breaks the mapping. Prefer named lexer rules over new literals, and if you must add a literal, re-verify every `T__n` mapping against the regenerated `JmesPathLexer.java`.

### 3. Lexer adapter (rarely edited)
- `src/main/kotlin/my/example/jmespath/JMESPathLexer.kt`
  - Wraps generated ANTLR lexer into IntelliJ `LexerBase`. Special-case at ~line 90: a `NAME` followed by `(` or matching `BUILTIN_FUNCTIONS` is re-tagged `FUNCTION`.

### 4. PSI element types (edit when adding a composite node)
- `src/main/kotlin/my/example/jmespath/JMESPathElementTypes.kt`
  - `JMESPathElementType` + `JMESPathElementTypes` object of `@JvmField` constants (`OBJECT_HASH`, `KEYVAL_EXPR`, `KEY_NAME`, ...). Add a new constant for each new node type you want in the PSI tree.

### 5. Hand-written parser — MUST mirror the grammar (edit for any grammar change)
- `src/main/kotlin/my/example/jmespath/JMESPathPsiParser.kt`
  - The actual runtime parser. Mirror every grammar rule change here.
  - `parseExpression`: operator precedence loop (`.`, `[`, comparators, `&&`, `||`, `|`).
  - `parsePrefix`: primary constructs — `(...)`, `{...}` (multi-select hash, ~lines 145–171), `[...]`, `!`, `&`, `` `...` `` literal, function call, atoms.
  - `parseSlice` / `isSliceAt`: slice `[start:stop:step]`.

### 6. Parser definition (rarely edited)
- `src/main/kotlin/my/example/jmespath/JMESPathParserDefinition.kt` — binds lexer + parser + element types to the language.

### 7. Syntax highlighting (edit when adding a token)
- `src/main/kotlin/my/example/jmespath/JMESPathSyntaxHighlighter.kt` — `TextAttributesKey` per token + `getTokenHighlights` `when` mapping.
- `src/main/kotlin/my/example/jmespath/JMESPathSyntaxHighlighterFactory.kt` — factory (usually no change).
- `src/main/kotlin/my/example/jmespath/JMESPathColorSettingsPage.kt` — attribute descriptors + demo text.

### 8. Formatting (edit when adding a token/node with spacing/indent needs)
- `src/main/kotlin/my/example/jmespath/formatting/JMESPathBlock.kt` — wrap/indent/spacing logic; `when` on `JMESPathElementTypes.*` and `JMESPathTokenTypes.*`.
- `src/main/kotlin/my/example/jmespath/formatting/JMESPathFormattingModelBuilder.kt` — `SpacingBuilder` rules (colon, comma, comparators).

### 9. Brace matching (edit when adding a bracket pair)
- `src/main/kotlin/my/example/jmespath/JMESPathPairedBraceMatcher.kt` — `BracePair` array.

### 10. Plugin registration (edit only when adding a new language feature, e.g. annotator/completion)
- `src/main/resources/META-INF/plugin.xml` — registers fileType, syntaxHighlighterFactory, parserDefinition, braceMatcher, colorSettingsPage, formatter.

### 11. Build config
- `build.gradle.kts` — `generateGrammarSource` task: `-visitor`, `-package my.example.jmespath`, output `build/generated-src/antlr/main/my/example/jmespath`.
- JDK: `corretto-17` at `~/.jdks/corretto-17.0.20.1`. Gradle has no `JAVA_HOME`; export it before every Gradle command.

### 12. Tests (edit to cover new/changed syntax)
- `src/test/kotlin/my/example/jmespath/JMESPathParserTest.kt` — PSI tree / element-type assertions (e.g. `KEYVAL_EXPR`, `KEY_NAME`).
- `src/test/kotlin/my/example/jmespath/JMESPathHighlightingTest.kt` — lexer token-stream assertions + highlighter + brace matcher.
- `src/test/kotlin/my/example/jmespath/JMESPathFormattingTest.kt` — formatting golden tests.

## Workflow

1. Edit `src/main/antlr/JmesPath.g4`.
2. Regenerate:
   ```bash
   ./gradlew generateGrammarSource
   ```
   Verify the new rule/token appears in `build/generated-src/antlr/main/my/example/jmespath/JmesPathParser.java` / `JmesPathLexer.java`.
3. Mirror the grammar change in `JMESPathPsiParser.kt`; add element types to `JMESPathElementTypes.kt` if a new composite node is introduced.
4. If new lexer tokens: add token types + `getIElementType` mapping in `JMESPathTokenTypes.kt`, and (if needed) highlighter keys in `JMESPathSyntaxHighlighter.kt` / color page. Re-check the fragile `T__n` mapping if you added literals.
5. If formatting/braces affected: update `JMESPathBlock.kt` / `JMESPathFormattingModelBuilder.kt` / `JMESPathPairedBraceMatcher.kt`.
6. Add/update tests in the three test files above.
7. Run:
   ```bash
   ./gradlew test
   ```

## Gotchas

- **Grammar vs. hand-written parser drift** is the top failure mode. The grammar generates visitor/listener APIs, but the PSI tree users actually see comes from `JMESPathPsiParser`. Always update both.
- **`T__n` renumbering** breaks `JMESPathTokenTypes.getIElementType`. See section 2.
- Lexer rule order matters in ANTLR: earlier rules win on equal match length (e.g. `JSON_CONSTANT` is declared before `NAME`, so `true`/`false`/`null` lex as `JSON_CONSTANT` everywhere).
- Parser rule names must start lowercase; lexer rule names UPPERCASE.
